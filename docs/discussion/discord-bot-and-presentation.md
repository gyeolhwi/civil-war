> **작성:** 2026-06-05 / 상태: 가이드 초안 (구현 전 검토)
>
> **목적:** ① 내전 진행용 "규칙 프레젠테이션 화면", ② 디스코드 봇/ API 연동을

## A. 규칙 프레젠테이션 화면 (쉬움 · 봇과 무관)

디스코드 화면공유로 라이브 진행할 때 보여줄 **전체화면 규칙/진행 화면**.

- **무엇:** `/present` 또는 `/app/present` 라우트. 큰 글씨·다크·슬라이드형으로
  - 밸런싱 규칙(티어 점수·조합 패널티 개요), 드래프트 순서(1-2-2-2-1 스네이크),
    밴 규칙, 현재 맵/밴/팀 편성 결과를 크게 표시.
- **데이터:** 이미 다 있음(domain 상수·매치 결과). 정적 규칙 + 현재 진행 중인
  매치를 props로.
- **난이도:** 낮음. 순수 웹. 봇 없이 독립적으로 먼저 가능.
- **선택지:** (a) 정적 규칙 슬라이드만, (b) 진행 중 매치 연동(편성·밴·맵 실시간 표시).
  → **(a)부터, 이후 (b)로 확장 권장.**

## B. 디스코드 봇 — 먼저 "봇이 어떻게 동작하나"

봇은 두 가지 방식으로 디스코드와 통신한다. **이 구분이 핵심.**

### 1) 게이트웨이(Gateway, WebSocket) — "항상 켜져 있는 프로세스"
- 봇이 디스코드와 **상시 연결**을 유지하며 실시간 이벤트를 받음
  (메시지·이모지 반응·음성채널 입퇴장·멤버 가입 등).
- **항상 떠 있는 서버가 필요** → Vercel 서버리스에선 불가. 별도 호스팅 필요
  (Railway, Fly.io, Render, 작은 VPS 등). 보통 `discord.js` 라이브러리.
- 일부 이벤트는 **privileged intent**(Message Content, Server Members 등) →
  개발자 포털에서 토글 + 검수 필요.

### 2) HTTP 인터랙션(Webhook) — "서버리스로 가능"
- **슬래시 커맨드**(`/내전`)나 버튼/모달 같은 인터랙션이 일어나면 디스코드가
  내 **HTTP 엔드포인트로 POST**를 보냄. 항상 떠 있을 필요 없음 → **Vercel API 라우트로 처리 가능.**
- 단, 이건 "사용자가 명령을 쳤을 때"만 옴. **반응/음성입퇴장 같은 수동 이벤트는 못 받음.**
- 요청 서명(Ed25519) 검증 필수.

### 3) REST API — "행동은 어디서든"
- 봇 토큰만 있으면 어디서든(서버리스 포함) 호출:
  메시지 전송, **메시지의 반응 단 사람 목록 조회**, 멤버를 **다른 음성채널로 이동**,
  채널 생성 등. `https://discord.com/api`.

> **요지:** "실시간 수동 이벤트(반응/음성)가 꼭 필요"하면 게이트웨이(별도 호스팅),
> "명령 칠 때 처리 + 필요할 때 REST로 조회"면 **서버리스(Vercel)로 충분**.

### 봇 만들기 준비물 (공통)
1. [Discord Developer Portal]에서 **Application 생성 → Bot 추가 → Bot Token**(비밀).
2. OAuth2 URL로 서버에 초대 (scope: `bot`+`applications.commands`, 권한: 메시지 보내기·
   반응 읽기·**멤버 이동(Move Members)**·채널 보기 등).
3. 토큰은 환경변수(서버 전용, `NEXT_PUBLIC_` 아님). DB 쓰기는 Supabase service_role.

## C. 우리 워크플로우에 매핑 (실현 가능성)

> 결론 먼저: **대부분 서버리스(Vercel API 라우트 + REST)로 가능.** 음성 자동분배만
> 약간 까다롭고, 실시간 반응 추적이 필요하면 그때 게이트웨이 추가.

### 사용 워크플로우
| # | 원하는 것 | 구현 방법 | 방식 | 난이도 |
|---|---|---|---|---|
| 1 | 관리자가 봇 실행 → 일정·시간 공지 | 슬래시 `/내전 날짜 시간` → 임베드 글 + ✅ 이모지 자동 첨부 | HTTP 인터랙션 | 낮음 |
| 2 | ✅ 단 인원 파악 | **반응 단 사람 목록을 REST로 on-demand 조회** (`GET .../reactions/✅`) | REST | 낮음 |
| 3 | 인원 리스트 확인 | 디스코드 user_id → 등록 멤버 매핑 후 목록 응답 | REST+DB | 중 |
| 3-후속 | 웹 "내전 시작"에서 스케줄 인원 프리셋 자동선택 | 스케줄별 참가자 스냅샷을 DB에 저장 → 멤버 선택 화면이 불러옴 | 웹+DB | 중 |
| 4 | 밴까지 끝난 팀 배정 디스코드 복사 | 이미 있음(`buildDiscordText`) — 단 **복사 텍스트에 디스코드 user_id 포함** 필요 | 웹 | 낮음 |
| 5 | 복사 내용 넣으면 A/B 음성채널 자동 분배 | 텍스트 파싱은 취약 → **웹이 배정 결과(+user_id)를 API로 봇에 push** → 봇이 REST로 멤버 이동 | REST | 중상 |

**5번 음성 이동 상세:**
- 멤버를 음성채널로 옮기는 건 REST 한 방(`PATCH /guilds/{guild}/members/{user}` + `channel_id`).
  봇에 **Move Members 권한** 필요, 대상이 **이미 음성채널에 들어와 있어야** 함.
- "복사-붙여넣기 텍스트 파싱"보다 **웹 → 봇 직접 전달**이 안정적
  (배틀태그≠디스코드ID라 텍스트만으론 매핑 불확실). 즉 5번은 4번 복사 대신
  웹에서 "디스코드로 팀 보내기" 버튼 → 봇 API 호출이 이상적.

### 디스코드 첫 워크플로우(온보딩)
| # | 원하는 것 | 구현 방법 | 비고 |
|---|---|---|---|
| 1 | 디스코드 온보딩으로 멤버등록 정보 API 전송 | **가능.** 단 등록 폼이 풍부(티어·포지션·선호영웅 최대5·맵)해서 **디스코드 모달(최대 5필드)론 비좁음** | 아래 권장안 |
| 2 | 본인 정보 항상 수정 | 웹 프로필 수정 = 이미 있음. 디스코드 ID로 키 연결 | |

**온보딩 권장안 2가지:**
- **(권장) 링크 방식:** `/등록` 치면 봇이 **본인 디스코드 ID가 박힌 웹 등록 링크**를 DM/응답.
  웹의 풍부한 폼으로 입력·저장(작성 시 `discord_user_id` 저장). 수정도 같은 링크.
  → 모달 한계 회피 + 기존 웹 폼 재사용. **가장 적은 작업.**
- (대안) 모달 방식: 배틀태그·디코명 정도만 모달로 빠르게, 티어·영웅은 웹에서 보강.

## D. 이 모든 걸 잇는 "한 줄짜리 핵심": `discord_user_id`

지금 봇이 못 붙는 이유는 **디스코드 계정 ↔ 등록 멤버를 잇는 키가 없어서**다.
- **`members`에 `discord_user_id text unique` 추가**(또는 매핑 테이블). 이거 하나면
  반응 단 사람 → 멤버, 팀 배정 → 디스코드 계정, 음성 이동이 전부 연결된다.
- 길드/채널 ID, 스케줄(공지)·참가 스냅샷 저장용 테이블도 필요.

예상 추가 스키마(초안):
```
alter table members add column discord_user_id text unique;        -- 계정 연결

create table discord_events (   -- 내전 공지(스케줄)
  id uuid pk, channel_id uuid→channels, message_id text,
  scheduled_at timestamptz, status text, created_at ...
);
create table discord_signups (  -- 공지에 ✅ 단 사람
  event_id uuid→discord_events, discord_user_id text, reacted_at ...,
  primary key (event_id, discord_user_id)
);
-- 길드/음성채널 매핑은 channels에 컬럼 추가 or 별도 테이블
```

## E. 권장 아키텍처 & 단계 (스택 그대로 활용)

**아키텍처: 우선 "서버리스 + HTTP 인터랙션"으로 시작.**
- Vercel API 라우트 `/api/discord/interactions`(서명검증) — 슬래시 커맨드 처리.
- 행동(반응 조회·메시지·음성이동)은 **REST**로. DB는 service_role.
- **별도 봇 서버 불필요.** 워크플로우 대부분(공지·참가자 조회·음성이동·온보딩 링크)
  이 방식으로 커버됨.
- *나중에* 실시간 반응 카운트/자동화가 꼭 필요하면 그때 게이트웨이 봇(Railway 등) 추가.

**단계 제안:**
- **Phase 0 (기반):** `members.discord_user_id` 추가 + 웹 프로필을 ID로 연결. (봇 없이도 의미)
- **Phase 1:** 규칙 프레젠테이션 화면(A). 독립·쉬움.
- **Phase 2:** HTTP 인터랙션 봇 — `/내전`(공지+✅), `/참가자`(반응→멤버 목록).
- **Phase 3:** 참가 스냅샷 → 웹 "내전 시작"에서 프리셋 자동선택.
- **Phase 4:** 웹 "디스코드로 팀 보내기" → 봇이 A/B 음성채널 자동 이동.
- **Phase 5(선택):** 게이트웨이 봇으로 실시간/온보딩 고도화.

## F. 결정 필요 / 열린 질문
- 음성 자동분배: **복사-붙여넣기 파싱** vs **웹→봇 직접 전달**(권장) 중 택1.
- 온보딩: **링크 방식**(권장) vs 모달.
- 봇 호스팅: 서버리스로 시작에 동의하는지(권장) / 처음부터 게이트웨이 둘지.
- A/B 음성채널은 고정 채널인지, 매번 생성인지.
- 디스코드 user_id 수집 시점(온보딩 강제 vs 선택).

> **다음 액션 후보:** Phase 0(`discord_user_id` 마이그레이션) 또는 Phase 1(프레젠테이션 화면)
> 부터. 봇 자체는 Phase 2에서 Discord Application 생성 후 시작.

## G. POC — 타당성 검증 결과 (2026-06-05)

> **POC = "실제로 구현 가능한지" 타당성 검증** (추정 X, 증거 O).
> ① Discord 공식 API 문서로 각 동작이 실재하는지 + ② 가장 불확실한 핵심을 **코드로 실행**.

### 가장 큰 불확실성을 코드로 증명 ✅
서버리스(Vercel) 봇이 성립하려면 **반드시** 통과해야 하는 단 하나의 관문 =
**Ed25519 인터랙션 서명검증 + PING→PONG**. 이걸 무의존성으로 실제 실행해 **7/7 통과**.

- 파일: `poc/discord-interactions-verify.mjs` (실행 `node poc/discord-interactions-verify.mjs`, 의존성 0, 앱과 무관)
- 결과: 정상 PING→200+PONG(type1) / 서명·본문·타임스탬프 **변조 전부 401** /
  슬래시 커맨드→type4 / **WebCrypto(Edge 런타임) 경로도 통과**.
- 의미: **Vercel 서버리스 함수가 Discord 인터랙션 엔드포인트로 동작 가능**함이 암호학적으로 확정.
  (별도 상시 봇 서버 없이 시작 가능 — 이게 최대 리스크였음.)

### 타당성 매트릭스 (문서 근거 + POC)
| 워크플로우 단계 | Discord 수단 | 근거 | 판정 |
|---|---|---|---|
| 서버리스 인터랙션 엔드포인트 | HTTP Interactions URL · Ed25519 · PING/PONG | 문서 + **POC 7/7** | ✅ 타당 |
| `/내전` 공지 + ✅ 첨부 | 슬래시(type2→콜백4) + REST 메시지/반응 | 문서(콜백 4·9) | ✅ 타당 |
| "✅ 단 사람" 조회 | `GET /channels/{ch}/messages/{msg}/reactions/{emoji}` | 문서(message) | ✅ 타당 (100/요청·`after` 페이지네이션, 내전 규모는 1요청) |
| 디스코드ID ↔ 멤버 연결 | `members.discord_user_id` 1컬럼 | 스키마 | ✅ 타당 |
| A/B 음성 자동분배 | `PATCH /guilds/{g}/members/{u}` `channel_id`, 권한 `MOVE_MEMBERS` | 문서 | ⚠️ **조건부** — 대상이 **음성채널 접속 중이어야**(미접속 시 400) |
| 온보딩 멤버등록 API | 슬래시→웹 등록 링크 DM / 모달(최대 5필드) | 문서(모달 type9) | ✅ 타당 (풍부한 폼은 링크 방식 권장) |
| 규칙 프레젠테이션 화면 | 순수 웹 | 기존 스택 | ✅ 자명(POC 불필요) |

### 솔직한 한계 (실 자격증명 없이는 확인 불가 — 다음 단계에서)
- 실제 **봇 토큰/서버 권한 부여**, **레이트리밋 실측**, Discord의 **주기적 엔드포인트 검증**
  실배포 통과(코드는 통과하나 실제 URL 등록 후 확인 필요), 게이트웨이 쓸 경우 **privileged intent 승인**.
- 음성 자동분배: "복사 텍스트 파싱"은 배틀태그≠디스코드ID라 취약 → **웹→봇 직접 전달** 권장(재확인).

### 판정 & 권장 다음 단계
- **종합: 타당(feasible).** 워크플로우 거의 전부 **서버리스 경로로 구현 가능**.
  유일한 조건부는 음성 분배(대상이 음성채널에 들어와 있어야 — 모인 사람들이라 자연스럽지만 미접속자는 못 옮김).
- **실 PoC→MVP 최소 단계(사용자 작업 필요):**
  1. Discord Developer Portal에서 **App 생성 → Public Key**를 Vercel env(`DISCORD_PUBLIC_KEY`)로.
  2. `poc/`의 검증 코드를 **`/api/discord/interactions` Next 라우트**로 이식(raw body 읽기 주의).
  3. `/내전` 커맨드 1개 등록 + Interactions Endpoint URL 등록 → **Discord 검증 통과 확인**.
  4. 통과하면 Phase 2 본격 시작.
