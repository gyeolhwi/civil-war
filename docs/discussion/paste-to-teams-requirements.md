## 2. 근본 긴장 — 두 패러다임

이 기능이 어려운 이유는 owkr와 civil-war가 **데이터 철학이 정반대**이기 때문입니다.

| | **즉석형 (owkr-match)** | **관리형 (civil-war 현재)** |
|---|---|---|
| 정체성 | 텍스트에서 즉석 생성, id=timestamp | DB의 영구 멤버 행 (`members`) |
| 티어 출처 | **붙여넣은 텍스트 안** | **DB `member_role_ratings`** |
| 참가자 | 휘발성 객체 (`Player`) | 등록 멤버 참조 (`Participant`) |
| "티어 없는 역할" | UNRANKED로 배정(감점) | **키 없음 = 배정 불가** (`team-builder.ts:26`) |
| 선호 표현 | 역할별 `!`/`?` 플래그 | `primaryRole`/`secondaryRole` 슬롯 |
| 결과 | 팀 배치 + 이미지 (끝) | 기록 → 승패 → **개인 통계** |

**"혼재"란 이 두 모델이 한 코드/한 데이터에 섞이는 것을 말합니다.** 아래 4장이 그 지도입니다.

## 3. 붙여넣은 텍스트의 의미 — 세 갈래 (다시 정의)

| | **안 A · 명단 매칭** | **안 B · 완전 파싱** | **안 C · 하이브리드** |
|---|---|---|---|
| 텍스트에서 뽑는 것 | 이름만 | 이름 + 티어 | 이름 + 티어 |
| 티어 출처 | DB | 텍스트 | 매칭=DB, 게스트=텍스트 |
| 미등록자 | 배정 불가(등록 유도) | 즉석 참가 | 즉석 참가 |
| 성격 | 기존 흐름의 **입력 단축** | **독립 계산기** | 둘의 다리 |

> **→ ✅ 확정: 안 B.** 티어 출처 = **텍스트**, 미등록/등록 구분 없이 **전원 즉석 참가**, **멤버 DB read 없음**(안 A/C의 DB 매칭 제거). "기존 로직과 무관·빠른편성 전용" 요구를 완전히 만족.

## 4. 혼재 지도 — 어디서·왜 섞이는가 (핵심)

두 모델을 이으려 할 때 충돌하는 지점은 정확히 **4곳**입니다.

### ① 정체성 충돌 (Identity)
붙여넣은 `홍길동#1234`가 DB 멤버 `홍길동#1234`와 같은 사람인가?
- 관리형의 모든 하위 흐름(드래프트 픽, `match_participants`, 통계)은 **`member_id`(실제 행)를 전제**합니다.
- 매칭 안 된 게스트는 `member_id`가 없음 → 관리형 흐름에 넣는 순간 "주인 없는 참가자"가 생김.

### ② 진실 충돌 (Source of Truth)
한 사람에게 **티어가 두 개**(DB rating vs 텍스트 표기)가 될 수 있음.
- 티어를 읽는 모든 지점(점수 계산 `scoring.ts`, 표시)이 "지금 어느 모드냐" 분기를 갖게 됨 → 전형적 혼재.

### ③ 기록·통계 충돌 (Persistence)
즉석 매치가 **개인 통계/승패에 반영되나?**
- 반영 O → 게스트는 귀속할 멤버 행이 없어 통계 오염.
- 반영 X → "기록되는 매치"와 "휘발 매치" **두 종류**가 생겨 히스토리·'다음 판' 흐름이 양쪽을 다 처리해야 함.

### ④ 타입·코드 충돌 (Type System)
owkr `Player`(역할별 `Rank` 내장, 대문자 `TANK`) ↔ civil-war `Participant`(`ratings` 부분맵, 소문자 `tank`).
- 서로 어댑터로 변환해야 하고, 한쪽이 다른 쪽 흐름으로 새면 버그.

### 충돌 위험 요약

| 충돌 지점 | 안 A | 안 B (격리) | 안 C |
|---|:---:|:---:|:---:|
| ① 정체성 | 없음 | 없음¹ | **높음** |
| ② 진실(티어) | 없음 | 없음¹ | **높음** |
| ③ 기록·통계 | 없음 | 낮음¹ | **높음** |
| ④ 타입·코드 | 없음 | 중간(어댑터 1개) | **높음** |

> ¹ **안 B의 위험이 낮은 건 "격리" 덕분입니다.** 즉석 참가자가 DB·통계를 절대 건드리지 않는 경계가 있으면, 두 모델이 애초에 만나지 않습니다. 이것이 6장의 골자.

## 5. 재구성된 결정 — "독립 메뉴"가 혼재를 가둔다

여기서 관점을 바꿔야 합니다.

> **파싱 방식(A/B/C)은 "앱 전체를 어떻게 바꾸나"가 아니라, "격리된 신규 메뉴가 *내부적으로* 어떤 데이터 출처를 쓰나"의 문제로 축소됩니다.**

이미 "독립 새 메뉴"로 확정했기 때문에, 신규 메뉴에 **하드 경계(no DB write, no stats)**를 두면 ①②③ 충돌은 **신규 메뉴 안에 갇힙니다**. 관리형 데이터는 오염되지 않습니다.

그래서 A/B/C의 실질 선택지는 이렇게 정리됩니다.

- **안 A** 는 사실상 "독립 메뉴"와 상충합니다. A의 본질은 *기존 마법사에 참가자를 채워주는 단축키*라서, 독립이 아니라 **통합**입니다. (원한다면 별개 소기능으로 병행 가능하나, 이 메뉴의 정체성은 아님.)
- **안 B (격리 계산기)** 가 "독립 메뉴 + 혼재 회피"에 **가장 잘 맞습니다.** owkr처럼 텍스트만으로 완결, DB를 안 건드리므로 관리형과 애초에 안 섞임. 단점(중복 구현)은 **밸런서를 병합**하기로 했으므로 크게 줄어듦(파서+얇은 어댑터만 신규).
- **안 C** 는 혼재 위험이 전방위 최고. 지금 단계에서는 비권장.

### 결정 (✅ 확정)

> **안 B(격리된 즉석 계산기)로 확정.** 완전 일회성 — **멤버 DB를 읽지도 쓰지도 않고**, 편성 결과도 저장하지 않는다.
> 📌 "정식 매치로 저장" 승격 다리는 **제외**(일회성 확정). 훗날 정말 필요해지면 그때 **명시적·단방향·수동** 액션으로만 재검토.

이러면: 독립 메뉴(격리) ✓ · 혼재 회피 ✓ · 밸런서 공유 ✓ · 구현 최소.

## 6. 목표 아키텍처 (경계 계약)

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  관리형 (기존)               │        │  즉석형 (신규 "빠른 편성")   │
│  DB 멤버 · 드래프트 · 통계   │        │  텍스트 파싱 · 격리 상태     │
│                             │        │  localStorage(선택) · no DB  │
│  Participant (DB)           │        │  파싱 결과 → 어댑터          │
└──────────────┬──────────────┘        └───────────────┬──────────────┘
               │  둘 다 같은 입력 형태로 변환해서 호출  │
               ▼                                        ▼
        ┌────────────────────────────────────────────────────┐
        │   공유 순수 밸런서 엔진 (team-builder.ts 확장)      │
        │   generateCandidates / assembleTeam / 품질지표      │
        │   — DB·저장·상태 전혀 모름. 순수 계산만.           │
        └────────────────────────────────────────────────────┘
               ▲ 단방향·수동 승격만 (2단계 옵션)
   즉석 편성 ──┘  "정식 매치로 저장" 클릭 시에만 관리형으로
```

**경계 규칙 3개**
1. 즉석형은 **DB에 쓰지 않는다** (읽기도 기본 안 함; C 채택 시에만 읽기 매칭).
2. 두 세계는 **밸런서 엔진(순수 함수)만 공유**한다. 상태·타입 정체성은 공유하지 않는다.
3. 즉석 → 관리형 이동은 **사용자가 누르는 단 하나의 명시적 액션**으로만.

## 7. 밸런서 병합 설계 ("둘 병합"의 구체안)

좋은 소식: **기존 `team-builder.ts`가 이미 owkr와 골격이 같고, 더 정리돼 있습니다.**

| | owkr `use-balance` | civil-war `team-builder` |
|---|---|---|
| 분할 생성 | 0번 고정 5+5 | 0번 고정 5+5 (`halfSubsets`) |
| 팀 배치 | 5×C(4,2) 완전탐색 | 동일 (`bestAssignment`) |
| 후보 정렬 | top-5 유지 | **전체 정렬 반환** (`generateCandidates`) |
| 순수성 | 훅 내부 | **이미 순수 함수** |

→ **엔진은 civil-war 것을 단일 소스로 유지**하고, owkr에서 **아이디어만** 이식합니다.

**civil-war 엔진에 추가할 것 (owkr에서 취함)**
- **품질 지표** — 역할별 매치업 차·팀 내 표준편차. 현재는 `diff`만 있음 → 순수 지표 함수 추가.
- **대안 후보 노출** — `generateCandidates`가 **이미 정렬 반환** → "다른 조합 보기"는 사실상 UI만.

**버릴 것 (혼재 유발)**
- owkr의 UNRANKED 감점 방식 → civil-war의 **"티어 없으면 배정 불가"** 규칙 유지 (일관성).

**어댑터 (즉석형 → 엔진 입력)**
파싱 결과를 `Participant` 형태로 변환:

| 파싱 결과 | → `Participant` 필드 |
|---|---|
| `TANK/DPS/SUPPORT` | `tank/dps/support` (소문자) |
| 역할별 `Rank.score` (>0) | `ratings[role]` (0이면 키 생략 = 배정불가) |
| `isPreferred` 역할 | `primaryRole` |
| 이름#태그 | `battleTag`, id=합성(`guest:...`) |
| heroes/maps | 빈 배열 (즉석은 영웅·맵 미사용) |

> 합성 id에 `guest:` 프리픽스를 강제해, 즉석 참가자가 관리형 흐름에 새면 **즉시 눈에 띄게** 합니다(경계 방어).

## 8. 기능 카탈로그 — 선택용 (구현 현실 포함)

각 기능의 **실제 구현 난이도/위험**을 붙였습니다. 이걸 보고 골라주세요.

### 8.1 확정 (요청 사항)

| 기능 | 구현 현실 |
|---|---|
| ⭐ 텍스트 붙여넣기 입력 | 신규 textarea + 파서. `@dnd-kit`처럼 기반 없음, 순수 신규 |
| ⭐ 드래그 팀원 교체 | `@dnd-kit` **이미 설치·미사용** → 바로 활용 |
| ⭐ 아이콘 가독성 (역할 SVG·티어 이미지·상태 아이콘) | 신규 컴포넌트. owkr `team-card`가 좋은 레퍼런스 |

### 8.2 선택 4종 → **✅ 전부 채택 (2026-07-14 확정)**

| # | 기능 | 채택 | 구현 현실 | 혼재 위험 |
|---|---|:---:|---|:---:|
| B2 | **대안 후보 + 교체** | ✅ | `generateCandidates` **이미 정렬 반환** → UI만 | 없음 |
| B3 | **밸런스 품질 지표** | ✅ | 순수 지표 함수 2~3개 추가(엔진 확장) | 없음 |
| P6/P7 | **선호/비선호 · 마이크 반영** | ✅ | ⚠️ `Participant`에 `noMic`·역할별 `avoided` **필드 없음** → 모델 확장 필요. **즉석형 로컬 타입에만** 확장(공유 타입 불가침) | 중간→낮음 |
| C1 | **결과 이미지 복사** | ✅ | 순수 UI(캡처). 격리 안전 | 없음 |

> **P6/P7 확정 조건:** 공유 `Participant`를 건드리지 말고 **즉석형 로컬 확장**으로만 둔다(경계 유지). 안 B는 애초에 멤버 DB를 안 읽으므로 이 확장이 관리형에 샐 여지 없음.

### 8.3 파서 하위 기능 (안 B/C 채택 시)

슬래시/공백/역할라벨/줄바꿈 다중 포맷 · 티어 약어(브~챔) · 디스코드 이모지 · 미배치(예상) · 중복제거 · 실패줄 배너. 대부분 owkr 파서를 **거의 그대로 이식** 가능.
