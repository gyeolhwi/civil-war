# 요구사항 정의서

- **프로젝트명**: Civil War — 오버워치 디스코드 채널별 내전 운영 웹앱
- **버전**: v1 (MVP)
- **작성일**: 2026-05-28
- **기준 게임 모드**: 오버워치 2, 5v5 (1탱-2딜-2힐)

---

## 1. 프로젝트 개요

### 1.1 한 줄 요약

디스코드 채널 단위로 분리된 오버워치 내전 모임을, 채널 관리자가 멤버를 등록하고 매주 정기적으로 팀을 편성·운영·기록할 수 있는 웹 애플리케이션.

### 1.2 운영 모델

- **단위**: 디스코드 채널 1개 = 독립된 내전 그룹 1개
- **주기**: 매주 금요일 저녁 1회 (채널별 자율)
- **참가자 수**: 채널당 멤버 10명 이상 등록 가능. 1회 내전 = 정확히 10명 선발 (5v5)
- **현재 채널 관리자**: 벙커, 옵무원, 오버워치코리아 등등

### 1.3 핵심 가치

- 관리자가 손으로 하던 팀 빌딩(티어 점수 합산, 조합 패널티 검토, 스네이크 드래프트)을 자동화
- 매주 누적되는 전적·통계를 채널 단위로 보관해 다음 시즌 개선에 활용
- 자가신고 티어 + 선호도 가중치로 최소한의 입력만으로 합리적 팀 분배

## 2. 사용자 및 권한

| 역할 | 권한 | 비고 |
|---|---|---|
| **슈퍼관리자** | 채널 생성, 채널 관리자 계정 발급/삭제 | DB 직접 입력 또는 별도 콘솔 |
| **채널 관리자** | 본인 소유 채널의 모든 운영 (멤버 등록·수정, 내전 진행, 결과 입력) | 일반 ID/PW 로그인 |
| **참가자(멤버)** | 시스템 로그인 없음 — 관리자가 대신 등록 | 자가 신고 정보를 관리자에게 전달 |

### 2.1 인증 방식

- **로그인**: **아이디(username) + 비밀번호**
- **회원가입**: 없음. 슈퍼관리자가 계정 발급
- **비밀번호 분실**: 슈퍼관리자가 재설정 (이메일 리셋은 v1.1)

#### 아이디 로그인 구현 노트

Supabase Auth는 내부적으로 이메일 기반이므로, 아이디 로그인을 다음과 같이 얹는다.

- 슈퍼관리자가 계정 발급 시 `username`과 내부 이메일(`{username}@civilwar.local` 규칙)을 함께 생성
- 로그인 화면은 아이디만 입력받고, 서버가 `username → 내부 이메일`로 변환 후 `signInWithPassword` 호출
- 사용자에게 이메일은 노출하지 않음 (순수 아이디 UX)
- `admins` 정보(username, 소유 채널)는 별도 관리 — §5 데이터 모델의 `channels.owner_admin_id`가 이를 참조

### 2.2 관리자 ↔ 채널 매핑

- **v1**: 1 관리자 = 1 채널 고정
- **DB 스키마**: N:M 관계로 미리 설계 (향후 다채널 운영 대비)

## 5. 데이터 모델 개요

### 5.1 엔티티 관계도 (개념)

```text
channels ──< channel_members >── members
              │       (배틀태그 글로벌 유니크)
              │
              ├──< member_role_ratings        (채널별 역할 티어)
              ├──< member_hero_preferences    (채널별 선호 영웅)
              └──< member_map_preferences     (채널별 선호 맵)

channels ──< matches ──< teams ──< team_members ──> members
                          (A/B)             (배정 포지션·사용 영웅·개인 점수·픽 순서)
```

### 5.2 엔티티 책임 요약

| 엔티티 | 책임 |
|---|---|
| `channels` | 디스코드 채널 단위 그룹. 슈퍼관리자가 생성. `owner_admin_id`(소유 관리자, 1:1 매핑) |
| `members` | **글로벌 멤버 마스터**. 배틀태그(유니크) + 디스코드 이름 등 신원 정보만 |
| `channel_members` | 채널 ↔ 멤버 매핑. 채널별 등록일·주/부 포지션 등 기본 프로필 |
| `member_role_ratings` | 멤버의 **채널별** 역할 티어 (탱/딜/힐 각각). PK: (channel_id, member_id, role) |
| `member_hero_preferences` | 멤버의 **채널별** 선호 영웅 (최대 5개). PK: (channel_id, member_id, hero_code) |
| `member_map_preferences` | 멤버의 **채널별** 선호 맵. PK: (channel_id, member_id, map_code) |
| `matches` | **한 판의 내전 = 1 레코드**. `channel_id`, `played_at`, `map_code`, `winner_side`, `score_a`, `score_b`, `banned_hero_a`, `banned_hero_b`, `memo` |
| `teams` | 매치당 A/B 2 레코드. `match_id`, `side`, `captain_id`, `total_score`, `combo_bonus`, `combo_penalty`, `final_score`, `is_winner` |
| `team_members` | 한 팀의 5명. `team_id`, `member_id`, `assigned_role`, `individual_score`, `hero_used`, `pick_order`(드래프트 모드 시 1~10, 자동 모드는 NULL) |

> 상세 필드와 관계는 별도 ERD 문서에서 확정 (요구사항·워크플로우 확정 후 작성)

### 5.3 멤버 모델 핵심 룰

- **멤버 식별은 글로벌**: 배틀태그가 시스템 전체에서 유니크. 같은 배틀태그로 두 번 등록 불가
- **프로필 데이터는 채널 단위로 분리**: 같은 멤버가 채널 A에서는 다이아 탱커, 채널 B에서는 골드 힐러로 등록 가능
- **채널 격리 (RLS)**: 채널 관리자는 자기 채널 데이터만 read/write. 다른 채널의 멤버 풀·프로필·매치 이력은 보이지 않음
- **글로벌 충돌 방지**: 멤버 등록 시 배틀태그 유니크 체크는 DB 레벨에서 수행. 다른 채널에 이미 등록된 배틀태그라도 UI상으로는 "신규 등록"으로 보이고, DB가 기존 `members.id`를 매핑해줌

### 5.4 영웅·맵 마스터 데이터 (v1 코드 상수 → 추후 DB 이관)

**원칙**: 결국 모든 마스터 데이터는 DB에 저장된다. 단 v1에서는 **TypeScript 코드 상수**로 시작하고, 상수의 shape을 **미래 DB 테이블과 1:1 대응**되게 설계해 나중에 마이그레이션이 그대로 떠지도록 한다.

#### `HEROES` 상수 (→ 미래 `heroes` 테이블)

| 필드 | 예시 | 비고 |
|---|---|---|
| `code` | `rein` | 참조 키 |
| `name_ko` | 라인하르트 | 표시명 |
| `role` | tank | tank/dps/support |
| `sub_roles` | `['brawl_tank']` | 1개 이상 (중복 영웅은 복수) |
| `normalized_sub_role` | brawl_tank | §6.3 정규화 결과 |
| `image` | `/heroes/rein.jpg` | 드래프트·밴·결과 화면 썸네일 |
| `is_active` | true | 비활성 영웅 숨김 |

#### `MAPS` 상수 (→ 미래 `maps` 테이블)

| 필드 | 예시 | 비고 |
|---|---|---|
| `code` | `kings_row` | 참조 키 |
| `name_ko` | 왕의 길 | 표시명 |
| `mode` | hybrid | escort/hybrid/control/push/flashpoint/clash |
| `image` | `/maps/kings_row.jpg` | 선호 입력·결과 화면 썸네일 |
| `is_active` | true | 로테이션 아웃 맵 숨김 |

#### 운영 규칙 (v1)

- DB의 `hero_code`·`map_code` 컬럼은 string 그대로 저장. zod enum으로 검증 (코드 상수의 `code` 집합과 동기화)
- 이미지는 `/public/heroes/`, `/public/maps/` 정적 에셋 (DB 이관 시 Supabase Storage로 이전)
- 신규 영웅·맵 추가 시 v1은 PR 1회, DB 이관 후에는 관리 UI에서 추가

\* 중복 표기 영웅 (정규화 룰은 §6.3 참조)

### 6.3 중복 표기 영웅 정규화 (자동, 사용자 선택 불가)

**원칙**: 한 영웅 = 한 서브유형으로 점수/조합 계산. 우선순위는 **큰 조합 패널티를 회피하는 쪽**.

**서브유형 우선순위 (역할별)**

- 딜러: `main_dps` > `playmaker_dps` > `utility_dps` (메인딜 부재 -300 회피 우선)
- 힐러: `main_support` > `utility_support` > `damage_support` (메인힐 부재 -500 회피 → 그다음 "둘 다 공격힐 -400"이 "둘 다 유틸힐 -250"보다 크므로 utility 우선)
- 탱커: `brawl_tank` > `poke_tank` > `dive_tank` (범용성 우선)

| 영웅 | 카탈로그 표기 | 시스템 정규화 |
|---|---|---|
| 라마트라 | brawl + poke | **brawl_tank** |
| 솜브라 | playmaker + utility | **playmaker_dps** |
| 키리코 | main + utility | **main_support** |
| 바티스트 | main + damage | **main_support** |
| 라이프위버 | main + utility | **main_support** |
| 미즈키 | damage + utility | **utility_support** |
| 우양 | damage + utility | **utility_support** |

### 6.4 신규 영웅 (서브유형 확정)

| 영웅 | 역할 | 서브유형 | 정규화 |
|---|---|---|---|

- 4단계: +100
- 3단계: +200
- 2단계: +300
- 1단계: +400

예: 다이아 2단계 = 5000 + 300 = **5300**, 챔피언 1단계 = 8000 + 400 = **8400**

### 7.2 선호도 가중치

| 상황 | 가중치 |
|---|---|
| 1순위 선호 포지션 | ×1.00 |
| 추가 가능 포지션 | ×0.90 |
| 선호 목록에 없지만 티어 있음 | ×0.75 |
| 티어 없음 | **배정 불가** |

### 7.3 개인 역할 점수 공식

```text
개인 역할 점수 = (배정 포지션 티어 점수) × (선호도 가중치)
```

> **결정사항 (#5)**: 선호 영웅 서브유형(브롤/다이브 등)과 실제 배정 포지션이 미스매치되더라도 개인 점수에는 별도 패널티 없음. 서브유형은 §8 팀 조합 패널티 계산에만 사용.

### 7.4 팀 점수 공식

```text
팀 점수 = (5인 개인 점수 합계) + (조합 보너스) - (조합 패널티)
```

## 8. 조합 패널티 룰

### 8.1 패널티 표

| 조건 | 패널티 |
|---|---|
| 메인딜 0명 | **-300** |
| 메인힐 0명 | **-500** |
| 딜러 2명이 같은 유형만 보유 | -150 |
| 힐러 2명이 모두 `damage_support` | -400 |
| 힐러 2명이 모두 `utility_support` | -250 |
| 탱커 유형과 딜러 방향성 크게 불일치 (§8.4) | -200 |

### 8.2 판정 기준

- 멤버의 **선호 영웅 서브유형** 집합을 기준으로 판정
- 한 멤버가 여러 서브유형 영웅을 선호하면 모두 보유로 인정 (예: 메인딜+변수딜 둘 다 보유)
- 중복 표기 영웅은 §6.3 정규화 룰 적용 (1영웅 = 1서브유형)

### 8.3 공정성 보정

- **최근 같은 팀 이력**: 직전 N판 동안 같은 팀이었던 빈도가 높으면 추가 패널티 (v1 가중치는 결과 보고 튜닝)

### 8.4 탱-딜 방향성 불일치 판정 (-200)

탱커의 교전 거리 성향과 딜러 라인이 맞지 않을 때 적용.

```text
교전 거리축:  근접 ←──────→ 원거리
  brawl_tank = 근접 (전선 압박)
  dive_tank  = 침투 (백라인)
  poke_tank  = 원거리 (견제)
```

**불일치 조건 (둘 중 하나라도 해당 시 -200)**

- `dive_tank`인데 딜러 2명 중 `playmaker_dps`(변수딜/플랭커)가 **0명** → 다이브를 받칠 화력 부재
- `poke_tank`인데 딜러 2명이 **모두 `playmaker_dps`** → 포킹 라인과 불일치

`brawl_tank`은 범용으로 간주하여 이 패널티에서 면제.

## 9. 내전 워크플로우 (요약)

> 상세는 별도 워크플로우 명세 문서에서 확정.

```text
[1] 관리자 로그인 (아이디+비번)
        ↓
[2] 채널 대시보드 (내전 시작 / 멤버 관리 / 전적·통계)
        ↓
[3] 채널 멤버 중 10명 선택
        ↓
[4] 모드 선택 (기본 / 팀장 4모드)
        ↓
[5] 팀 빌딩
   - 기본: 밸런스 후보 10개 중 랜덤
   - 팀장(최고티어): 점수 상위 2명 → 스네이크 드래프트
   - 팀장(탱커): 탱커 가능자 상위 2명 → 스네이크 드래프트
   - 팀장(예능): 점수 하위 2명 → 스네이크 드래프트
   - 팀장(직접): 관리자가 2명 지정 → 스네이크 드래프트
        ↓
[6] 드래프트 진행 (팀장이 포지션 지정해서 픽)
    └ 픽 1건마다 양 팀의 점수·조합 보너스/패널티 실시간 갱신·표시
        ↓
[7] 최종 팀 확정 (A팀 / B팀 / 점수 표시)
        ↓
[8] 맵 자동 선정 (참가자 선호 맵 합집합에서 랜덤)
        ↓
[9] 영웅 밴 (팀당 1명)
        ↓
[10] 내전 진행
        ↓
[11] 결과 입력 (승팀·스코어·사용 영웅·메모)
        ↓
[12] 다음 판? (같은 팀 한 판 더 / 맵만 변경 / 처음부터 재편성 / 세션 종료)
```

### 9.1 팀장 결정 모드 — 상세

| 모드 | 팀장 선정 기준 | 용도 |
|---|---|---|
| **최고티어 모드** | 점수 상위 2명 (자동) | 표준 |
| **탱커 모드** | 탱커 유형 가능자 중 상위 2명 (자동) | 탱커 영향력 강조 |
| **예능 모드** | 점수 하위 2명 (자동) | 난장판 컨셉 |
| **직접 지정 모드** | 채널 관리자가 2명을 직접 선택 (수동) | 사전 약속·특정 멤버 강조 |

### 9.2 기본 팀 생성 알고리즘

1. 가능한 모든 5+5 팀 분배 조합 생성
2. 각 조합의 팀 점수 계산 (§7.4)
3. 두 팀 점수 차이 절댓값으로 정렬
4. 차이가 가장 적은 **상위 10개 조합** 중 무작위 선택

### 9.3 드래프트 픽 순서 (5v5)

팀장 2명이 이미 각 팀에 배치된 상태에서 **남은 8명을 스네이크로 8픽**.

스네이크 방식: **1-2-2-2-1** (총 8픽)

- **드래프트 시작 전 팀장 2명이 자기 포지션을 먼저 지정** (W1 확정)
- 1팀장 → 2팀장 → 2팀장 → 1팀장 → 1팀장 → 2팀장 → 2팀장 → 1팀장
- 팀장이 픽 시 **배정 포지션을 함께 지정** (선호와 다른 포지션 가능)
- 상세: `docs/workflow.md` [5-B], [6]
- **실시간 점수 표시**: 매 픽 후 각 팀의 `total_score` / `combo_bonus` / `combo_penalty` / `final_score`를 즉시 재계산해 양 팀 상단 패널에 표시. 점수 차이를 보며 다음 픽 결정 가능
- 점수 변동 시 시각적 강조(증가는 초록, 감소는 빨강 잠깐 하이라이트)

### 9.4 결과 입력 → 데이터 매핑 (§9 [11])

내전 종료 후 관리자가 한 화면에서 일괄 입력. 저장 시 **단일 트랜잭션**으로 처리해 부분 저장 방지.

#### 입력 항목 → 저장 위치

| 입력 항목 | 저장 위치 | 타입·비고 |
|---|---|---|
| 승팀 (A/B) | `matches.winner_side` | enum `'A' \| 'B'` (무승부 시 NULL) |
| A팀 스코어 | `matches.score_a` | 정수 (오버워치 게임 내 점수) |
| B팀 스코어 | `matches.score_b` | 정수 |
| A팀 5명 사용 영웅 (**선택**) | `team_members.hero_used` × 5건 | `hero_code`, nullable. 이름 타이핑 자동완성 |
| B팀 5명 사용 영웅 (**선택**) | `team_members.hero_used` × 5건 | 동일 |
| 메모 | `matches.memo` | 자유 텍스트 (선택) |

> **필수는 승팀·스코어만.** 영웅·메모는 선택. 영웅 입력은 이름 일부만 쳐도 매칭되는 자동완성으로 빠르게(예: "라인"→라인하르트). 미입력 영웅은 통계에서 "미기록".

#### 자동 갱신 항목 (별도 입력 없음)

| 항목 | 갱신 위치 | 산출 방식 |
|---|---|---|
| 팀별 승패 플래그 | `teams.is_winner` × 2건 | `winner_side`로부터 결정 |
| 개인 통계 (승률·평균 점수 등) | **저장 안 함** | F12 조회 시 `team_members` JOIN으로 즉석 집계 |

#### 결과 입력 화면 UX (참고)

```text
[ A팀 (승리) ]                   [ B팀 ]
─────────────                    ─────────────
홍길동  탱  [라인하르트 ▾]      김홍도  탱  [윈스턴 ▾]
이순신  딜  [솔저:76    ▾]      장영실  딜  [트레이서 ▾]
...                              ...

승팀: ( ● A   ○ B )
스코어: [ 2 ] : [ 1 ]
메모: [_______________________]
                          [저장]
```

## 10. 비기능 요구사항

### 10.1 성능

- 팀 빌딩은 **항상 참가자 10명 고정** → 1탱-2딜-2힐 조합 수가 적어 brute-force 즉시 계산
- 팀 빌딩 응답 시간 < 1초

### 10.2 보안

- Supabase Row Level Security (RLS)로 채널 격리 강제
- 관리자는 본인 채널의 데이터만 read/write 가능
- 슈퍼관리자 전용 라우트는 별도 미들웨어로 보호

### 10.3 가용성

- Vercel 자동 배포 + Preview Deploy
- DB 백업: Supabase 자동 백업 (Pro 플랜 시 PITR)

### 10.4 접근성·반응형·디자인

- 모바일 사용 케이스는 v2 (드래프트는 데스크탑 위주 가정)
- **다크 캔버스 기반** (Linear 다크 시스템) — 디자인 토큰·컴포넌트·모션은 `docs/design.md` 참조
- **화면 공유 전제**: 드래프트 점수 변동 등 핵심 상태 변화는 모션으로 명확히 (과하지 않게)
- **UX는 토스 철학**: 한 화면 한 가지 일, 즉각 피드백, 되돌릴 수 있는 흐름 (design.md UX 원칙)
- `prefers-reduced-motion` 존중
